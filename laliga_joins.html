Why JOINs Exist

One table seems easier — until you try to keep it correct. Build a La Liga database, watch a single table fall apart, then split it in two and stitch it back together with a JOIN.

Goals Setup 1 · The problem 2 · Split it 3 · The JOIN Traps Practice

✓ What you will be able to do

By the end of this page you can:

  • Explain what goes wrong when the same fact is stored on many rows.
  • Split one wide table into two tables joined by an id.
  • Write a SELECT that pulls columns from both tables using JOIN … ON, and filter it with WHERE.

⚙ Setup — load the La Liga data

Six Spanish clubs, four players each. Small enough to check by eye.

Create a database and load the file (it is safe to run more than once — it rebuilds everything):

The steps in Terminal
psql -U postgres
CREATE DATABASE laliga; 
\c laliga
\i laliga.sql

Check you have what you should have — 24, 24 and 6:

SQL
SELECT COUNT(*) FROM players_flat;
SELECT COUNT(*) FROM players;
SELECT COUNT(*) FROM teams;

Load the file with -f or \i — some names contain accents (Atlético de Madrid), which can get mangled if you type them straight into a Windows terminal.

1 The problem: one big table

The "obvious" design — put everything about a player in one row.

Here is players_flat. It has one row per player and carries the club's name, city and stadium along for the ride:

SQL
SELECT player_name, position, team_name, city, stadium
FROM players_flat
ORDER BY player_id
LIMIT 5;
player_name position team_name city stadium
Thibaut Courtois Goalkeeper Real Madrid Madrid Santiago Bernabéu
Éder Militão Defender Real Madrid Madrid Santiago Bernabéu
Jude Bellingham Midfielder Real Madrid Madrid Santiago Bernabéu
Vinícius Júnior Forward Real Madrid Madrid Santiago Bernabéu
Marc-André ter Stegen Goalkeeper FC Barcelona Barcelona Camp Nou

The highlighted cells are the same three facts typed again on every player's row.

How much is repeated?

Count it. There are 24 rows, but the club information is only really six different things:

SQL
SELECT COUNT(*) AS all_rows,
       COUNT(DISTINCT team_name) AS distinct_clubs
FROM players_flat;
Result
 all_rows | distinct_clubs 
----------+----------------
       24 |              6
(1 row)

Six facts, written 24 times. That is the crack the rest of this lesson widens.

Problem 1 — fixing a typo means finding every copy

Sevilla's ground gets a new name. You must update every player row for that club:

SQL
UPDATE players_flat
SET stadium = 'Estadio Ramón Sánchez-Pizjuán'
WHERE team_name = 'Sevilla FC';
Result
UPDATE 4

UPDATE 4 — four rows changed for one fact. And if you miss a row, your data now disagrees with itself:

SQL
SELECT DISTINCT team_name, stadium
FROM players_flat
WHERE team_name = 'Sevilla FC';
Result
 team_name  |            stadium            
------------+-------------------------------
 Sevilla FC | Estadio Ramón Sánchez-Pizjuán
 Sevilla FC | RSP
(2 rows)

⚠ Same club, two stadiums

Nothing stopped that. The table has no idea those two rows are describing the same club — it just stores whatever text you give it.

Problem 2 — you cannot store a club that has no players yet

Valencia CF joins the league, but you have not signed anyone. There is nowhere to put the club, because a row is a player. So you end up inventing an empty player:

SQL
INSERT INTO players_flat (player_id, player_name, position, team_name, city, stadium)
VALUES (25, NULL, NULL, 'Valencia CF', 'Valencia', 'Mestalla');
Result
INSERT 0 1
SQL
SELECT * FROM players_flat WHERE player_id = 25;
Result
 player_id | player_name | position |  team_name  |   city   | stadium  
-----------+-------------+----------+-------------+----------+----------
        25 |             |          | Valencia CF | Valencia | Mestalla
(1 row)

⚠ A player who is not a player

Row 25 has a club but no person. Any query that counts players now has to remember to ignore it.

Problem 3 — deleting a player can delete a club

Sevilla is relegated, so you clear out their players. Watch what happens to the club:

SQL
DELETE FROM players_flat WHERE team_name = 'Sevilla FC';
SQL
SELECT COUNT(*) AS rows_left,
       COUNT(DISTINCT team_name) AS clubs_left
FROM players_flat;
Result
 rows_left | clubs_left 
-----------+------------
        20 |          5
(1 row)

Sevilla FC was a real club with a real stadium. It is simply gone — deleted along with its players, even though nobody asked to delete the club.

↺ Put it back

You have just deleted rows. Re-run the loader to start clean:

psql -U postgres -d laliga -f laliga.sql

💡 The name for all this

Repetition causes update, insert and delete problems like these. The fix is always the same: store each fact once, and point at it from everywhere else.

2 Split it into two tables

Facts about a club live with the club. Facts about a player live with the player.

Now the club is stored once, in its own table, and gets a number to be known by:

SQL
SELECT team_id, team_name, city FROM teams ORDER BY team_id;
team_id team_name city
1 Real Madrid Madrid
2 FC Barcelona Barcelona
3 Atlético de Madrid Madrid
4 Athletic Club Bilbao
5 Sevilla FC Sevilla
6 Real Sociedad San Sebastián

🔑 The join key

players.team_id holds the same numbers as teams.team_id. That shared column is called the join key — it ties the two tables together. Without it, nothing connects them.

3 Put it back together with a JOIN

The split is only worth it if you can rebuild the full picture on demand. That is what JOIN does.

You want player names and club names in one result — but they live in different tables. Ask for both, and tell the database how the tables are linked:

SQL
SELECT p.player_name, t.team_name
FROM players AS p
JOIN teams   AS t ON t.team_id = p.team_id;

p and t are just short nicknames for the two tables. The ON line is the link: for each player, find the club whose team_id matches that player's team_id.

Add a few more columns and you have rebuilt the flat table — except each fact is still stored only once:

SQL
SELECT p.player_name, p.position, t.team_name, t.city
FROM players p
JOIN teams t ON t.team_id = p.team_id
ORDER BY p.player_id
LIMIT 8;
Result
      player_name      |  position  |  team_name   |   city    
-----------------------+------------+--------------+-----------
 Thibaut Courtois      | Goalkeeper | Real Madrid  | Madrid
 Éder Militão          | Defender   | Real Madrid  | Madrid
 Jude Bellingham       | Midfielder | Real Madrid  | Madrid
 Vinícius Júnior       | Forward    | Real Madrid  | Madrid
 Marc-André ter Stegen | Goalkeeper | FC Barcelona | Barcelona
 Ronald Araújo         | Defender   | FC Barcelona | Barcelona
 Pedri                 | Midfielder | FC Barcelona | Barcelona
 Robert Lewandowski    | Forward    | FC Barcelona | Barcelona
(8 rows)

💡 A correct join never changes the count

The full join returns 24 rows — the same 24 players you started with, each with the right club attached.

! The two ways a join goes wrong

Learn these now and you will spot your own bugs in seconds.

Trap 1 — no link at all (the accidental 144)

If you list two tables but never say how they match, PostgreSQL pairs every player with every club. It does not warn you:

SQL
SELECT COUNT(*) FROM players, teams;
Result
 count 
-------
   144
(1 row)

⚠ Where does 144 come from?

24 players × 6 clubs = 144. Every player is glued to every club, so the answer is nonsense — and it is 6× too big. If a join gives you a suspiciously large number, look for a missing ON.

With the modern JOIN syntax, PostgreSQL refuses to run a join with no link, so that mistake announces itself:

Result
ERROR:  syntax error at or near ";"
LINE 1: SELECT COUNT(*) FROM players JOIN teams;
                                               ^

The old comma style is the dangerous one — it runs happily and quietly hands you 144 rows.

Trap 2 — the wrong link (a plausible wrong answer)

Matching the wrong columns runs perfectly and gives you a number that looks fine. Here we accidentally match the club's id to the player's id:

SQL — note the mistake
SELECT p.player_name, t.team_name
FROM players p
JOIN teams t ON t.team_id = p.player_id;
Result
      player_name      |     team_name      
-----------------------+--------------------
 Thibaut Courtois      | Real Madrid
 Éder Militão          | FC Barcelona
 Jude Bellingham       | Atlético de Madrid
 Vinícius Júnior       | Athletic Club
 Marc-André ter Stegen | Sevilla FC
 Ronald Araújo         | Real Sociedad
(6 rows)

⚠ No error, wrong answer

Militão plays for Real Madrid, not Barcelona. Because player 2's id happens to equal Barcelona's id, the query invented a pairing. The database cannot know which columns you meant — only you do. Always check the ON line: it should match team_id to team_id.

Recap — the one thing to remember

A JOIN needs two things: which tables, and how they match. The matching column is the join key — here, team_id on both sides.

Storing each fact once keeps your data correct; the join puts it back together whenever you need the full picture. Reset the data any time with psql -U postgres -d laliga -f laliga.sql.
