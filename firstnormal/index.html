First and Second Normal Form

One table, twenty-four players, and the same club details written out again and again. Fix it one rule at a time — without changing a single fact.

Goals Setup 1 · One big table 2 · 1NF 3 · 2NF Practice

✓ What you will be able to do

By the end of this page you can:

  • Say what first normal form requires, and name the rule our table breaks.
  • Say what second normal form requires, and decide which columns belong to which table.
  • Split one wide table into two, then prove that no information was lost.

⚙ Setup — load the data

Six Spanish clubs, four players each. Small enough to check by eye.

Create the database and load the file. It is safe to run more than once — it rebuilds everything:

The steps in Terminal
psql -U postgres
CREATE DATABASE firstnormal;
\c firstnormal
\i players.sql

Check you have what you should have — 24, 24, 24, 6 and 6:

SQL
SELECT COUNT(*) FROM players_flat;
SELECT COUNT(*) FROM players_1nf;
SELECT COUNT(*) FROM players_2nf;
SELECT COUNT(*) FROM teams;
SELECT COUNT(*) FROM clubs_bad;

Load the file with -f or \i — some names contain accents (Atlético de Madrid, San Mamés), which can get mangled if you type them straight into a Windows terminal.

The file builds the same facts several ways, so you can compare them side by side: players_flat (before), players_1nf (after 1NF), players_2nf + teams (after 2NF) — plus clubs_bad, a deliberate mess used in Part 2.

1 The problem: one big table

The "obvious" design — put everything about a player in one row.

Here is players_flat. It has one row per player, and carries the club's name, city and stadium along for the ride:

SQL
SELECT player_id, player_name, position, team_name, city, stadium
FROM players_flat
ORDER BY player_id
LIMIT 5;
player_id player_name position team_name city stadium
1 Thibaut Courtois Goalkeeper Real Madrid Madrid Santiago Bernabéu
2 Éder Militão Defender Real Madrid Madrid Santiago Bernabéu
3 Jude Bellingham Midfielder Real Madrid Madrid Santiago Bernabéu
4 Vinícius Júnior Forward Real Madrid Madrid Santiago Bernabéu
5 Marc-André ter Stegen Goalkeeper FC Barcelona Barcelona Camp Nou

Highlighted cells hold the same three facts over and over.

How much repetition is that?

There are only 6 clubs in this database. But the club's three columns are written out on all 24 rows — that is 72 cells holding just 18 pieces of information. Every time you type Santiago Bernabéu, you are storing a fact you already stored three rows earlier.

Ask the database how many clubs are really in there:

SQL
SELECT COUNT(*) AS rows, COUNT(DISTINCT team_name) AS clubs
FROM players_flat;
Output
 rows | clubs
------+-------
   24 |     6
(1 row)

COUNT(DISTINCT …) counts each club once, however many times its name is repeated. That gap — 24 rows pretending to be 6 clubs — is the repetition we are about to remove.

2 First normal form — one fact per cell

Three rules. We break each one, then fix it.

The 1NF rules

1. Every value is atomic — one fact per cell. Not a list, and not two facts glued together.
2. No repeating groups — no player1, player2, player3 columns.
3. Every row is uniquely identified by a primary key.

Rule 1 — one fact per cell

Start with a table that breaks it badly. clubs_bad lists each club's players inside a single cell:

SQL
SELECT * FROM clubs_bad;
Output
     club_name      |                             players
--------------------+------------------------------------------------------------------
 Real Madrid        | Thibaut Courtois, Éder Militão, Jude Bellingham, Vinícius Júnior
 FC Barcelona       | Marc-André ter Stegen, Ronald Araújo, Pedri, Anthony Gordon
 Atlético de Madrid | Jan Oblak, José María Giménez, Koke, Antoine Griezmann
 Athletic Club      | Unai Simón, Óscar de Marcos, Oihan Sancet, Iñaki Williams
 Sevilla FC         | Ørjan Nyland, Loïc Badé, Nemanja Gudelj, Dodi Lukébakio
 Real Sociedad      | Álex Remiro, Igor Zubeldia, Brais Méndez, Mikel Oyarzabal
(6 rows)

Six rows, and twenty-four players. Now ask the database how many players it is holding:

SQL
SELECT COUNT(*) FROM clubs_bad;
SELECT COUNT(*) FROM players_flat;
Output
 count
-------
     6
(1 row)

 count
-------
    24
(1 row)

Same 24 players, two different answers — because in clubs_bad the database can only see 6 rows. It has no idea how many players are hiding inside those cells.

And the questions get worse. This is the query you actually want to write:

SQL
SELECT COUNT(*) FROM clubs_bad WHERE position = 'Goalkeeper';
Output
ERROR:  column "position" does not exist

⚠ The data is in there — but you cannot reach it

Every player's position is sitting in that cell as part of the text. The database cannot count them, sort them, or join to them, because they are not values — they are words inside a sentence. Data you cannot query is data you do not really have.

The fix is to give every player their own row. That is exactly what players_flat does — and it is why it has 24 rows. One list, spread downwards into a column:

SQL
SELECT player_id, player_name, position FROM players_flat ORDER BY player_id LIMIT 4;
Output
 player_id |   player_name    |  position
-----------+------------------+------------
         1 | Thibaut Courtois | Goalkeeper
         2 | Éder Militão     | Defender
         3 | Jude Bellingham  | Midfielder
         4 | Vinícius Júnior  | Forward
(4 rows)

Rule 1 applies inside a column too. Look closely at player_name — it is still holding two facts in one cell:

SQL
SELECT player_name FROM players_flat ORDER BY player_id LIMIT 3;
Output
   player_name
------------------
 Thibaut Courtois
 Éder Militão
 Jude Bellingham
(3 rows)

'Thibaut Courtois' is a first name and a last name crammed into one box. You cannot sort the class list by surname, and you cannot search for everyone called Jude, without taking the text apart. Split it into two columns:

player_name (players_flat) first_name last_name
Thibaut Courtois Thibaut Courtois
Marc-André ter Stegen Marc-André ter Stegen
Óscar de Marcos Óscar de Marcos
Pedri Pedri NULL

NULL is a real answer

Two of our players — Pedri and Koke — go by one name only. There is no surname to store, so last_name is NULL. That means no value, which is exactly right. Do not invent a surname just to fill the gap.

Rule 2 — no repeating groups

The second way to break rule 1 is to spread the list sideways instead of downwards:

club_name player1 player2 player3 player4 player5
Real Madrid Thibaut Courtois Éder Militão Jude Bellingham Vinícius Júnior ?

Same mistake, different costume: how many columns do you allow? A club with five players breaks it, and half the columns sit empty for a club with three.

Rule 3 — give every row a key

players_flat still has no PRIMARY KEY. Without one, nothing stops the same player being stored twice. Try it:

SQL
INSERT INTO players_flat (player_id, player_name, position, team_name, city, stadium)
VALUES (7, 'Pedri', 'Midfielder', 'FC Barcelona', 'Barcelona', 'Camp Nou');
Output
INSERT 0 1

The database accepted it without complaint. Pedri is now in the table twice — and the two rows are completely identical.

⚠ Two identical rows, and no way to tell them apart

Suppose you spot the mistake and try to correct one of them:

UPDATE players_flat
SET position = 'Forward'
WHERE player_name = 'Pedri';
UPDATE 2

It changed both rows. There was no way to point at just one, because nothing in the table makes one row different from the other. That is what a primary key is for.

The fix is one line. In the data file, players_1nf is players_flat with this added:

SQL
ALTER TABLE players_flat ADD PRIMARY KEY (player_id);

(The file builds it as a separate table instead, so that players_flat stays un-fixed and you can keep comparing the two.)

Run the same duplicate insert against players_1nf:

SQL
INSERT INTO players_1nf (player_id, first_name, last_name, position, team_name, city, stadium)
VALUES (7, 'Pedri', NULL, 'Midfielder', 'FC Barcelona', 'Barcelona', 'Camp Nou');
Output
ERROR:  duplicate key value violates unique constraint "players_1nf_pkey"
DETAIL:  Key (player_id)=(7) already exists.

The database refuses. That is first normal form.

So what actually changed?

This is why players_1nf does not look like players_flat any more — three things moved, and not one fact was edited:

players_flat players_1nf
the player's name player_name — one cell first_name + last_name
primary key none player_id
rows 24 24
the club's details repeated on all 24 rows still repeated — Part 3's job

↺ If you ran that duplicate insert

You now have 25 rows in players_flat. Reload the file to get back to 24: psql -U postgres -d firstnormal -f players.sql.

3 Second normal form — one table, one subject

Ask what each column is actually describing.

The 2NF rule

A table is in 2NF when it is already in 1NF, and every non-key column describes the key — and nothing but the key. No column should be describing some other thing that just happens to be sitting in the same row.

players_1nf has its key: player_id. Now read the seven columns and ask what each one is really about.

column describes same on all four Real Madrid rows?
player_id the player no
first_name the player no
last_name the player no
position the player no
team_name the club yes
city the club yes
stadium the club yes

The transfer test

Courtois signs for Barcelona tomorrow. Which columns have to change?

player_id, first_name, last_name, position — unchanged.
team_name, city, stadium — all three change, together, always.

Three columns that only ever move as a set are not describing the player. They are describing the club — and they are in the wrong table.

So split them. The player keeps their own facts and a reference to their club; the club's facts move to a table of their own, stored once each:

players_1nf
player_id
first_name
last_name
position
team_name
city
stadium
→
players_2nf
player_id
first_name
last_name
position
team_name
teams
team_name
city
stadium

player facts · club facts · reference to a club

Where did city and stadium go?

Look at players_2nf and you will not find city or stadium anywhere. They have not been deleted — they have moved into teams, and team_name is the thread that ties them back to each player.

That is the right home for them. A player's city only ever changes when their club changes, so the city is a fact about the club. Keep it here and you would be back to typing it out on all 24 rows.

SQL
CREATE TABLE teams (
  team_name VARCHAR(60) PRIMARY KEY,
  city      VARCHAR(60),
  stadium   VARCHAR(80)
);

INSERT INTO teams (team_name, city, stadium)
SELECT DISTINCT team_name, city, stadium
FROM players_flat;

SELECT DISTINCT is what pulls the clubs out of the repeated rows — 24 rows go in, 6 come out. That is the repetition disappearing.

SQL
CREATE TABLE players_2nf (
  player_id INT PRIMARY KEY,
  first_name VARCHAR(40),
  last_name VARCHAR(40),
  position VARCHAR(20),
  team_name VARCHAR(60) REFERENCES teams(team_name)
);

That REFERENCES makes team_name a foreign key: the database will now refuse a player whose club does not exist, exactly as it refused the duplicate player in Part 2:

SQL
INSERT INTO players_2nf (player_id, first_name, last_name, position, team_name)
VALUES (25, 'Test', 'Player', 'Forward', 'Real Betis');
Output
ERROR:  insert or update on table "players_2nf" violates foreign key constraint "players_2nf_team_name_fkey"
DETAIL:  Key (team_name)=(Real Betis) is not present in table "teams".

What the split buys you

Barcelona renames its stadium. In the flat table you have to find and change every row that mentions it:

Before — on players_flat
UPDATE players_flat
SET stadium = 'Spotify Camp Nou'
WHERE team_name = 'FC Barcelona';
Output
UPDATE 4

After the split, the same rename touches one row:

After — on teams
UPDATE teams
SET stadium = 'Spotify Camp Nou'
WHERE team_name = 'FC Barcelona';
Output
UPDATE 1

⚠ Four rows to get right, or one

Forget one of those four rows in the flat table and your database now holds two different stadiums for the same club — and nothing tells you which one is correct. That is the real cost of repetition: not the disk space, but the chance of being wrong.

Nothing was lost

Join the two tables back together and you have the original view again:

SQL
SELECT p.first_name, p.last_name, p.position, t.team_name, t.city, t.stadium
FROM players_2nf p
JOIN teams t ON t.team_name = p.team_name
ORDER BY p.player_id
LIMIT 3;
Output
 first_name | last_name  |  position  |  team_name  |  city  |      stadium
------------+------------+------------+-------------+--------+-------------------
 Thibaut    | Courtois   | Goalkeeper | Real Madrid | Madrid | Santiago Bernabéu
 Éder       | Militão    | Defender   | Real Madrid | Madrid | Santiago Bernabéu
 Jude       | Bellingham | Midfielder | Real Madrid | Madrid | Santiago Bernabéu
(3 rows)

Every fact we started with is still there. Now count what the join hands back:

SQL
SELECT COUNT(*)
FROM players_2nf p
JOIN teams t ON t.team_name = p.team_name;
Output
 count
-------
    24
(1 row)

24 — one row per player. Nothing was dropped, and nothing was duplicated. The city and the stadium came back with them, because team_name matched every player to their club.

✓ "But team_name is still on every player row!"

Yes — and that is fine. It is now a short reference to a row in teams, not a copy of the club's details. The city and the stadium are stored once. Pointing at a fact is cheap; repeating it is what causes trouble.

Recap — the one thing to remember

Normalising never changes the facts, only where they live.

1NF — one fact per cell, no repeating groups, and a primary key on every table.
2NF — every column describes the key and nothing but the key. If a column is really describing something else, that something else needs its own table.
Reset the data any time with psql -U postgres -d firstnormal -f players.sql.
